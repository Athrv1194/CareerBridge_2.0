# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Security Constraints
- Always verify that `.env` files, API keys, database credentials, and any sensitive secrets are explicitly in `.gitignore` before executing any git commit or git push
- Never write sensitive API keys directly into any codebase file

## Systemic Incident & Bug Logging
Whenever you make a mistake, encounter a bug, or fix a performance issue, log it in `ai_incident_log.md` at the project root.

Requirements:
1. MANDATORY: Read and review `ai_incident_log.md` at the beginning of any new task before making changes
2. Ensure `ai_incident_log.md` is in `.gitignore` before writing to it
3. Log entries must be a table with these columns:
   - Timestamp (UTC)
   - Category (Bug / Error / Performance / Security)
   - Severity (SEV-1 Critical / SEV-2 High / SEV-3 Medium / SEV-4 Low)
   - Component (file, service, or feature affected)
   - Description & Diagnostics
   - Root Cause
   - Fix / Action Taken

## Incident Log Review
Before starting any new task, debugging, or implementing a fix — read `ai_incident_log.md` first to avoid repeating past mistakes.

## Project overview

CareerBridge is a Spring Boot microservices project (Spring Boot 4.1.0, Java 21, Maven). Each service is an independent Maven project under its own top-level directory, with no shared parent POM or shared library module — they are only related by convention (identical package/folder layout, adjacent ports, common `com.careerbridge.<service>` base package).

Services and their ports/datastores:

| Service | Dir | Port | Datastore | Notes |
|---|---|---|---|---|

**Aggregated view (the one evaluators should use): http://localhost:8080/swagger-ui.html.** api-gateway's `springdoc.swagger-ui.urls` lists all 11 backend services; the dropdown switches between them. This works by 11 additional gateway routes (`*-service-docs` in `application.yml`) that rewrite `/api-docs/<service>` to that service's own `/api-docs` — a plain passthrough route doesn't work here, since (unlike the `/api/**` routes) the gateway-facing path and the backend's real path differ. Each backend service's `OpenApiConfig` also hardcodes `http://localhost:8080` as its OpenAPI `servers` entry, overriding springdoc's request-derived default (which would otherwise report the container-internal hostname, e.g. `http://auth-service:8081`, breaking "Try it out" through the aggregated UI even though browsing the docs would look fine). See `ai_incident_log.md` (2026-08-03) for the full incident trail on both of these.

`auth-service` is the only backend service with its own Spring Security filter chain; its `SecurityConfig` explicitly `permitAll`s `/api-docs/**`, `/swagger-ui/**`, `/swagger-ui.html`, `/webjars/**` alongside its existing public auth endpoints. The other 9 backend services have no Spring Security on the classpath at all, so this only mattered for auth-service.

## Common commands

Each service is built and run independently from its own directory (no root aggregator POM).

```bash
# Build a service (from inside e.g. auth-service/)
./mvnw clean install

# Run a service locally
./mvnw spring-boot:run

# Run all tests for a service
./mvnw test

# Run a single test class
./mvnw test -Dtest=ClassNameTest

# Run a single test method
./mvnw test -Dtest=ClassNameTest#methodName

# Package (skip tests)
./mvnw clean package -DskipTests
```

On Windows without a shell that resolves `./mvnw`, use `mvnw.cmd` instead (each service ships its own Maven wrapper — `.mvn/`, `mvnw`, `mvnw.cmd`).

Since there's no root POM, building/testing "the whole project" means repeating the above per service directory — there's no single command that builds all six at once.

**Test dependencies are Boot 4's split `*-test` starters, not `spring-boot-starter-test`.** No service declares the latter; each pulls `spring-boot-starter-{webmvc,data-jpa,validation,actuator}-test` instead, and `webmvc-test` is what transitively supplies JUnit 5 + Mockito. Do not add `spring-boot-starter-test` — it is already there indirectly.

Frontend (from inside `careerbridge-frontend/`):

```bash
npm install
npm run dev       # Vite dev server
npm run build     # production build
npm run lint      # oxlint (NOT eslint) -- config in .oxlintrc.json
npm run preview   # serve the production build
```

`VITE_API_BASE_URL` in a gitignored `.env` points the frontend at the gateway (`http://localhost:8080/api`).

The whole stack is containerized — `docker compose --env-file .env up -d --build` brings up 14 containers (postgres, rabbitmq, 11 backend services, api-gateway). ai-coach-service is the only backend service that uses neither postgres nor rabbitmq, so its compose block deliberately inherits neither the `*backend-defaults` nor the `*backend-env` anchor. Only the gateway (8080), postgres (host 5434) and rabbitmq (5672/15672) publish host ports. Postgres runs with `max_connections=300` (raised from the image default of 100 — ten PostgreSQL-backed services sharing HikariCP's default pool of 10 each hit that ceiling with zero headroom the moment resume-service became the tenth; see resume-service's own notes below). The list below is what each service expects when run directly on the host with `mvnw spring-boot:run` instead:
- PostgreSQL on `localhost:5432`; the 8 databases (`careerbridge_auth`, `_student`, `_assessment`, `_recommendation`, `_notification`, `_organization`, `_roadmap`, `_prs`) must be created manually first — `CREATE DATABASE ...;` — PostgreSQL has no `createDatabaseIfNotExist` JDBC flag the way MySQL did. Under Docker `docker/init.sql` creates them, but **only on a fresh volume**
- MongoDB — **notification-service uses MongoDB Atlas (cloud), not a local mongod**. The `mongodb+srv://` URI embeds credentials and lives only in that service's gitignored `application-local.yml`. No other service has a Mongo dependency. The property is **`spring.mongodb.uri`**, not `spring.data.mongodb.uri` — see the notification-service notes below.
- SMTP: Gmail on `smtp.gmail.com:587` (notification-service only). Needs a Gmail **App Password**, not the account password, and 2FA enabled on the account.
- RabbitMQ on `localhost:5672`, default `guest`/`guest` (recommendation/notification services)

## Git workflow

`feature/<name>` → `dev` → `main`. All four branches exist on `origin`.

- One feature branch per service, cut from `dev` (`feature/auth`, `feature/student`).
- Merge into `dev` with `--no-ff` so each service lands as a reviewable merge bubble rather than a flattened fast-forward.
- Verify the build is green on `dev` after merging **before** pushing.
- Do not commit directly to `dev` or `main` for service work.

## Architecture conventions

Every service follows the identical layered package structure under `src/main/java/com/careerbridge/<service>/`:

- `controller/` — REST controllers
- `service/` — business logic; interface (`XService`) + implementation (`XServiceImpl`) pair
- `repository/` — Spring Data repository interfaces (JPA for PostgreSQL services, Mongo for notification-service)
- `model/` — JPA entities / Mongo documents
- `dto/` — request/response DTOs, kept separate from `model/`
- `config/` — `SecurityConfig`, `JwtConfig` (auth only), `RabbitMQConfig` (any service that publishes or consumes: auth, student, recommendation, notification)
- `exception/` — `GlobalExceptionHandler` + `CustomException`
- `event/` — event payload classes for cross-service messaging (auth, student, recommendation, notification)
- `consumer/` — RabbitMQ listener classes (`StudentEventConsumer` in student-service, `NotificationEventConsumer` in notification-service)
- `constants/` — service-scoped constant holders, private ctor, no instantiation (`JwtConstants` in auth, `SkillConstants` in student)
- `filter/` — servlet filters (`JwtAuthenticationFilter` in api-gateway and auth-service)
- `util/` — service-specific helpers (e.g. `ProfileCompletionCalculator` in student-service, `ScoringEngine` in assessment-service)

Cross-service event flow via RabbitMQ, all on the topic exchange `careerbridge.exchange`. Each consumer declares its own queue and binding; the publisher declares only the exchange.

| Event | Routing key | Publisher | Consumers | Status |
|---|---|---|---|---|
| `StudentRegisteredEvent` | `student.registered` | auth-service | student-service (creates the profile), notification-service (stores contact details), prs-service (initialises the score row + harvests `organizationId`) | **three consumers implemented** — each on its own queue |
| `AssessmentCompletedEvent` | `assessment.completed` | assessment-service | recommendation-service | **recommendation-service consumer implemented.** notification-service deliberately does NOT consume this — see Pending Tasks |
| `RecommendationGeneratedEvent` | `recommendation.generated` | recommendation-service | notification-service (email + in-app notification), roadmap-service (generates the milestone roadmap), prs-service (40% of the Placement Readiness Score) | **three consumers, each on its own queue.** All three legs verified live |
| `OrganizationCreatedEvent` | `organization.created` | organization-service | *(none yet)* | **published, deliberately unconsumed.** No queue is declared for it — a future consumer declares its own, per the ownership rule above |
| `RoadmapUpdatedEvent` | `roadmap.updated` | roadmap-service | prs-service (30% of the Placement Readiness Score) | **consumed since prs-service landed** — that service is the "future placement-service" roadmap-service's comments refer to |
| `PrsUpdatedEvent` | `prs.updated` | prs-service | *(none yet)* | **published, deliberately unconsumed.** Intended for a future dashboard service. No queue declared, same rule as `organization.created` |
| `ApplicationSubmittedEvent` | `application.submitted` | recruiter-service | *(none yet)* | **published, deliberately unconsumed.** A future notification-service consumer (e.g. "your application was received") declares its own queue, per the ownership rule above |
| `ApplicationStatusUpdatedEvent` | `application.status.updated` | recruiter-service | *(none yet)* | **published, deliberately unconsumed.** Same as above — a future "you were shortlisted/rejected" notification is the intended consumer |
| `ResumeGeneratedEvent` | `resume.generated` | resume-service | prs-service (activates the previously-reserved 10% resume slot), student-service (sets `StudentProfile.resumeUrl`, worth 15% of profile completion) | **two consumers, each on its own queue.** Both legs verified live, including a probe queue on the routing key itself |

| `careerbridge.student.resume.queue` | student-service | `resume.generated` |
| `careerbridge.recommendation.queue` | recommendation-service | `assessment.completed` |
| `careerbridge.notification.queue` | notification-service | `recommendation.generated` |
| `careerbridge.notification.student.queue` | notification-service | `student.registered` |
| `careerbridge.roadmap.queue` | roadmap-service | `recommendation.generated` |
| `careerbridge.prs.user.queue` | prs-service | `student.registered` |

Configuration is `application.yml` per service (not `.properties`). Each service's `spring.application.name` matches its directory name. Auth-service specifics worth knowing before touching it or consuming its events:
- Event contract published on registration: exchange `careerbridge.exchange` (topic, durable), routing key `student.registered`, JSON body `{userId, email, firstName, lastName, role, organizationId, registeredAt}`. Consumers declare their own queue and binding.
- Local credentials live in a gitignored `application-local.yml` (profile `local`, active by default via `spring.profiles.active: ${SPRING_PROFILES_ACTIVE:local}`). Never put a real password in `application.yml`.
- `/api/auth/refresh` is intentionally `permitAll` — it is called because the access token expired.
- Boot 4 gotchas already hit here: use `JacksonJsonMessageConverter` (Jackson 3), not `Jackson2JsonMessageConverter`; `UserDetailsServiceAutoConfiguration` now lives in `org.springframework.boot.security.autoconfigure`.

Student-service specifics worth knowing before touching it or copying its patterns:
- **No Spring Security on the classpath, by design.** `userId` arrives in the `X-User-Id` header, forwarded by the gateway after it validates the JWT; this service never parses tokens. `config/SecurityConfig.java` is a deliberately empty stub. Consequence: port 8082 must not be publicly reachable — anyone who can hit it directly sets that header to any value and acts as that student. Enforce with a security group / bind address at deploy time.
- Consumes `student.registered` on its own queue `careerbridge.student.queue`, bound to `careerbridge.exchange` with `TopicExchange(EXCHANGE, true, false)` — durable/autoDelete args must match auth-service's declaration exactly or RabbitMQ answers `406 PRECONDITION_FAILED` and the consumer silently never starts.
- The `@RabbitListener` parameter must stay the concrete `StudentRegisteredEvent`. Spring AMQP's default `TypePrecedence.INFERRED` resolves the payload from the method signature, which is the only reason the differing package FQN between auth and student works with zero type-mapper config. Widening it to `Object`/`Message` falls back to the sender's `__TypeId__` header → `ClassNotFoundException`.
- The consumer's copy of the event declares `role` as `String`, not an enum: wire-identical, but a duplicated enum would make Jackson hard-fail every event the day auth-service adds a seventh role.
- Consumer is intentionally **not** `@Transactional` and swallows all exceptions. The `unique` constraint on `student_profiles.userId` is the real idempotency guarantee; rethrowing would requeue and spin the listener forever.
- `addCertificate` deliberately skips the completion recalculation — certificates carry 0% weight, so it would be a no-op costing 4 queries. Pinned by `addCertificate_Success_DoesNotRecalculate`; give certificates a weight and that test fails.
- Profile completion basic-info block is all-or-nothing (all five of firstName/lastName/phone/bio/city, or zero of the 20%). Blank strings count as absent, because `PUT /profile` is a full replace where null clears a field.
- **`StudentProfile.role` and `GET /api/student/profiles/public` were added to support recruiter-service's candidate search**, not for anything student-facing. `role` is nullable with no `@Builder.Default` — a `NOT NULL` column with no `DEFAULT` fails `ddl-auto`'s `ALTER` against the already-populated table (the `Question.updatedAt` incident, again). The consumer now stores `event.getRole()`, which it previously discarded. `findByIsPublicTrueAndRole(String)` **replaced** the old unfiltered `findByIsPublicTrue()`, so a stale caller is a compile error, not a silent bug. **Adding this column is two changes, not one**: the `ALTER` and a backfill. Verified empirically rather than assumed: after the `ALTER`, all pre-existing rows held `role = NULL`, and the candidate pool returned `[]` — the schema change succeeded while the feature broke silently. Existing rows were backfilled from `careerbridge_auth.users` by hand (cross-database, so no single SQL statement can do it) and the resulting role distribution cross-checked against auth-service exactly. Any environment restored from a dump predating this column needs the same backfill, or its candidate pool comes back empty with no error anywhere. `GET /api/student/profiles/public` reads `X-User-Role` (required) and is restricted in the service layer to `RECRUITER`/`PLACEMENT_OFFICER`/`ORG_ADMIN`/`SUPER_ADMIN` — a `STUDENT` calling it would otherwise enumerate every other public profile on the platform.
- **A second RabbitMQ consumer, `onResumeGenerated` on its own `careerbridge.student.resume.queue`, sets `StudentProfile.resumeUrl` — worth 15 of `ProfileCompletionCalculator`'s 100 points, and nothing wrote this field before resume-service existed.** Every student was permanently capped at 85% completion until 2026-08-01. Routed through a new `StudentService.updateResumeUrl` method (not straight to the repository from the consumer) because the write needs `recalculate()`'s private path — the same one every other mutating method already uses — or the completion percentage would silently desync the instant `resumeUrl` changed. `StudentServiceImpl` gained its first `Logger` for this. Accepted edge case: deleting a student's *last* resume in resume-service does not clear `resumeUrl` here, since there is no `resume.deleted` event — the student keeps the 15% and a URL that now 404s until they generate a new one.

Assessment-service specifics worth knowing before touching it:
- **Option weights must never reach the client.** Enforced structurally: `OptionDto` has no `weight` field, and `submitAttempt` reads `weightEarned` from the stored `Option` row, never from the request payload.
- **`orderIndex` in responses is the position in that response, not the stored value.** In the seed data the highest-weighted option is always `order_index = 1`, so echoing the DB value back would let a client sort by it and pick the best answer every time — defeating the option shuffle. Renumbering is a security fix, not cosmetics.
- Each attempt draws `QUESTIONS_PER_ATTEMPT` (5) questions at random from the category, reshuffled per call, with options shuffled too. Which 5 were shown is **not persisted**, so `submitAttempt` can only verify answers are ≤5 valid questions from the category, not that they were the ones displayed. Closing that needs a `selected_question_ids` column.
- `maxPossibleScore` = `QUESTIONS_PER_ATTEMPT × MAX_OPTION_WEIGHT` (15), a fixed server-side denominator. Not the category total (larger, so a full answer set would score under 100%) and not the answer count (client-controlled, so one perfect answer would be 100%). The answer-count cap in `validateAndScore` is what stops a client submitting every category question against that fixed denominator.
- `data.sql` re-runs on every startup (`spring.sql.init.mode: always`). It is idempotent **only because** of the unique constraints on `questions(category_id, order_index)` and `options(question_id, order_index)` — `INSERT ... ON CONFLICT DO NOTHING` (PostgreSQL; was `INSERT IGNORE` under MySQL) suppresses nothing without them. See `ai_incident_log.md`; this broke startup once already under MySQL, and the MySQL→PostgreSQL conversion itself introduced a second, self-inflicted data-corruption incident — also logged.
- **Every `@Lob String` field was migrated to `@Column(columnDefinition = "TEXT")`.** Hibernate's `PostgreSQLDialect` maps a bare `@Lob String` to the `oid` large-object type (MySQL's dialect mapped the same annotation to `LONGTEXT`), which rejects a plain string value from either `data.sql` or a normal `repository.save(...)`. Affects `CareerPath.description`, `Category.description`, `Question.questionText`, `AssessmentResult.allCareerScoresJson` here, plus 3 fields in student-service. See `ai_incident_log.md`.
- **`data.sql` now supplies `created_at` explicitly** on every seeded row in `career_paths`, `categories`, and `questions`. `@CreationTimestamp` only fires on Hibernate's own insert path, never on a raw SQL script; MySQL silently substituted an implicit default for the missing `NOT NULL` value (outside strict mode), but PostgreSQL always rejects it. `options` has no `@CreationTimestamp` column and needed no change.
- `spring.jpa.defer-datasource-initialization: true` is a **Boot** property. Under `spring.jpa.properties.hibernate` it is silently ignored and `data.sql` runs before the tables exist.
- **`AssessmentCompletedEvent.allCareerScores` carries every career; `AssessmentResult.allCareerScoresJson` carries only the top `TOP_CAREERS_TO_RECOMMEND`.** Same-sounding names, different contents, deliberately: the event feeds recommendation-service's full ranking, while the persisted JSON is what `AssessmentResultDto` returns to the client and stays capped. Pinned by `submitAttempt_PublishedEvent_CarriesAllCareerScores`.
- Adding a field to the event is backward compatible with consumers holding an older copy — Jackson 3 (`tools.jackson`, what Boot 4 ships) disables `FAIL_ON_UNKNOWN_PROPERTIES` by default, verified by round-tripping the 9-field payload into an 8-field replica through `JacksonJsonMessageConverter`. Removing or renaming a field is still breaking.

Recommendation-service specifics worth knowing before touching it:
- **No `career_paths` table.** The 7 careers live in `constants/CareerCatalog.java` as a `List<CareerPathDto>` constant, not an entity — nothing in this schema references a career by id, so a table would add ddl-auto surface and a `data.sql` idempotency risk for zero capability. It is a second copy of assessment-service's `data.sql` seed and **must be kept in the same order** — see the next point.
- **`CareerCatalog.ALL`'s order is load-bearing.** It mirrors assessment-service's `data.sql` insert order, which is the order its `findAll()` returns and therefore what its stable sort falls back to on a tie. This service's own ranking ties the same way today (see below), so the two orderings must be edited together or rank 1 can silently diverge between the two services.
- **The `assessment.completed` event carries no map of career scores** — 8 scalar fields only, and `topCareerPath`/`careerMatchPercentage` are nullable. The full 7-career ranking is recomputed locally via `RecommendationEngine.calculateMatchScore`, a byte-for-byte mirror of assessment-service's `ScoringEngine` relevance heuristic (`1.0` if `requiredSkills` contains the category name, else `0.3`).
- **Only 2 of assessment-service's 5 categories have seeded questions today, and neither matches any career's `requiredSkills`.** So every real event currently scores all 7 careers at `0.3` relevance (ceiling 30.0) — a 7-way tie. Rank 1 in that case is decided by a tie-break that prefers the event's own `topCareerPath` name, falling back to `CareerCatalog.ALL` order if it's null or unrecognized. There is deliberately **no minimum-score threshold** on `topRecommendations` (`isTopRecommendation = rank <= TOP_CAREERS_COUNT` only) — a threshold above 30.0 would make it permanently empty against today's data.
- **`CareerRanking.rank` needs a quoted column name.** `RANK` is a reserved word in both MySQL 8.0.2+ and PostgreSQL (ANSI SQL:1999 window-function keyword); `hibernate.auto_quote_keyword` defaults off and nothing in this project enables it, so an unquoted `rank` column fails `ddl-auto` at startup. Fixed via `@Column(name = "\"rank\"")` — verified against live MySQL 9.0.1 (error 1064 without the fix) and again against live PostgreSQL 18.4 in both DDL and DML (insert + `ORDER BY`) after the database migration.
- **`findByUserIdAndIsActiveTrue` returns a `List`, not an `Optional`.** Originally because MySQL has no partial unique index. **Now on PostgreSQL, which does support one** (`CREATE UNIQUE INDEX ... WHERE is_active`) — the `List` design was kept as-is during the DB migration rather than revisited, since two concurrent `assessment.completed` events racing is already handled gracefully (reads take the newest, writes deactivate every row found) and a partial index would only add a second, redundant guarantee. Worth reconsidering if this service is ever revisited for its own sake, not as a side effect of the database swap.
- `overallMatchPercentage` and `topCareerName` on `Recommendation` are always read from this service's **own** rank 1, never copied from the event's `careerMatchPercentage`/`topCareerPath` — keeps the response internally consistent even if the two catalogs ever drift.
- Publishes `recommendation.generated`, now consumed by notification-service on `careerbridge.notification.queue`. End-to-end delivery has **not** been verified against a live broker yet — do it with docker-compose.

Notification-service specifics worth knowing before touching it:
- **`spring.mongodb.uri`, NOT `spring.data.mongodb.uri`.** Boot 4 moved driver-level Mongo settings into `spring.mongodb.*`; the old key is deprecated at level **`error`** since 4.0.0, which means Boot neither binds it nor warns — the driver silently falls back to `localhost:27017` and database `test`. This shipped in the Initializr scaffold and cost a real debugging session; logged SEV-2 in `ai_incident_log.md`. `spring.data.mongodb.*` still exists but only for Spring-Data-level settings (`auto-index-creation`, `field-naming-strategy`, `gridfs.*`).
- **Two queues, not one.** `careerbridge.notification.queue` (`recommendation.generated`) and `careerbridge.notification.student.queue` (`student.registered`). Two `@RabbitListener` methods on a *single* queue would create two containers consuming it, and RabbitMQ round-robins between them — roughly half of each event type would be bound into the wrong class. Jackson 3 has `FAIL_ON_UNKNOWN_PROPERTIES` off, so that does not throw; it yields an all-null object the null guard discards with a WARN, and half the notifications vanish with no error anywhere.
- **`UserContact` exists because `RecommendationGeneratedEvent` carries no email address.** `student.registered` is consumed purely to harvest `email`/`firstName`/`lastName` into a bridge table, looked up when a recommendation arrives. Consequence: a student who registered *before* this service first ran has no contact row — their email is skipped, but the in-app notification is still created and the `NotificationRecord` is written `FAILED` with the reason. That path is pinned by a test.
- **Write order in `processRecommendationNotification` is load-bearing: Mongo → email → Postgres audit row.** The state that must never occur is "audit row says SENT, no in-app notification, and the unique constraint now blocks every retry" — the student would silently never see their result. In this order a Mongo outage aborts before anything irreversible; the naive order makes that bad state the guaranteed outcome of any Mongo hiccup.
- **No `@Transactional` anywhere in this service, deliberately.** Boot auto-configures only a `JpaTransactionManager`, so it would cover neither the Mongo write nor the SMTP call while pinning a JDBC connection across a multi-second SMTP round trip. The two JPA writes are single statements, already transactional inside `SimpleJpaRepository.save`. Consistency comes from write *order* instead. There is a class-level comment saying so — please do not "restore the convention".
- **`NotificationDocument.createdAt` is set explicitly by the service.** `@CreationTimestamp` is `org.hibernate.annotations.*` and does nothing on a Mongo document — it would silently leave the field null and break the `OrderByCreatedAtDesc` feed ordering.
- **`isRead` is a `Boolean`, never a primitive**, with `@Builder.Default = false`. A primitive makes Lombok emit `isRead()`, collapsing the JSON property to `read` and silently breaking the frontend contract; a missing `@Builder.Default` writes `null`, and a Mongo query for `{isRead: false}` does not match `null`, so every new notification would be invisible to the unread count. Both are pinned by tests.
- **No `@Indexed` on the Mongo document.** `MongoMappingContext.autoIndexCreation` defaults to `false`, so it would be a silent no-op, and enabling it would make a reachable Mongo a hard startup requirement for every developer and for CI. If the feed query ever gets slow, create the index by hand in `mongosh` and note it here.
- **`management.health.mail.enabled: false`** — `MailHealthIndicator` opens a real SMTP connection to Gmail on every health poll; an ALB polling every 10s means ~8,600 handshakes a day and near-certain throttling. Also note `/actuator/health` here aggregates **three** datastores (Postgres + Mongo + RabbitMQ), so it is the most fragile of the five behind a naive health check — the ALB must use `/actuator/health/liveness`.
- **JavaMail has no default timeouts** and SMTP runs on the `@RabbitListener` thread at concurrency 1, so one hung Gmail connection would stall every subsequent notification indefinitely. `connectiontimeout`/`timeout`/`writetimeout` are all set to 5000ms.
- The controller is `/api/notification` (**singular**) to match the existing gateway route `Path=/api/notification/**`; gateway predicates match whole segments, so a plural mapping would 404 every request arriving through the gateway.
- `EmailService` is a concrete `@Service` with no interface — one implementation, and Mockito mocks classes fine. `buildHtmlBody` is public only so the base-package test can call it directly.

Organization-service specifics worth knowing before touching it (first P1 service):
- **This is the first service whose behaviour depends on `X-User-Role`.** That header did not exist before this service; adding it required extending api-gateway (see its section below). Anything else that starts reading a gateway-injected header must verify the gateway both *injects* it and *strips* the client's copy — the second half is the one that gets forgotten.
- **RBAC lives entirely in `OrganizationServiceImpl`, never in the controller or the gateway.** The gateway validates the JWT and forwards identity but knows nothing about which tenant owns a row. `requireCanAccessOrganization` is the single choke point: SUPER_ADMIN passes everything, ORG_ADMIN passes only its own org, everything else is 403.
- **`Objects.equals(callerOrgId, organizationId)`, never `==`.** Both are `Long` objects well outside the Integer cache, so `==` is false for exactly the ids the check exists to allow. A null `callerOrgId` can never match, which is the right outcome for an ORG_ADMIN whose token carries no organization.
- **403 is thrown *before* the row is loaded**, so probing ids cannot distinguish "exists but forbidden" from "does not exist". Pinned by `getOrganizationById_OrgAdmin_OtherOrg_Throws403`, which asserts the repository was never called.
- **`getAllOrganizations` refuses ORG_ADMIN with 403 rather than narrowing to their own org.** Silently returning a one-element list would make the same endpoint mean two different things depending on the caller.
- **`X-User-Org-Id` is `required = false` on every endpoint that reads it.** SUPER_ADMIN has no organization, so the gateway sends no header; marking it required 400s every SUPER_ADMIN request before the service is reached.
- **`deactivateOrganization` is a soft delete and SUPER_ADMIN-only.** Hard deletion would strand every student/assessment/recommendation row carrying the organization id; letting a tenant delete itself would do the same.
- **Publishes `organization.created` fail-soft** — the row is already committed when the publish runs, so rethrowing would report failure for work that actually happened, and the retry would then trip the duplicate-name check. Pinned by `createOrganization_BrokerDown_StillSucceeds`.
- **Declares no queue**, only the exchange. Nothing consumes `organization.created` yet; a queue bound with no listener accrues messages forever and looks like an unprocessed backlog.
- `UpdateOrganizationRequest` treats null as "leave unchanged", not "clear" — a partial update that nulled unset fields would wipe an address every time someone renamed an organization.
- **No `UserDetailsServiceAutoConfiguration` exclude**, unlike auth-service. That class only exists with the security starter on the classpath, and naming an absent class in `spring.autoconfigure.exclude` fails startup outright.
- **`docker/init.sql` only runs on a fresh postgres data directory.** `careerbridge_organization` was added to that file, but an existing `postgres-data` volume will never execute it — create the database by hand (`docker exec careerbridge-postgres psql -U postgres -c "CREATE DATABASE careerbridge_organization"`) or `docker compose down -v` first. Same applies to every future service added to `init.sql`.

Roadmap-service specifics worth knowing before touching it (second P1 service):
- **The 7 `careerName` values in `data/RoadmapDataSeeder.java` must match recommendation-service's `constants/CareerCatalog.java` byte for byte.** That service names the career in the `recommendation.generated` payload and this one looks the template up by that name. A rename on either side is silent: the lookup misses, the consumer logs a WARN, and every affected student simply gets no roadmap. Verified at build time by diffing the two lists; do the same after any edit. Note this is now the **third** copy of the career list, after assessment-service's `data.sql` and `CareerCatalog` itself.
- **`GET /api/roadmap/my` returns the newest roadmap whatever its status — it must NOT filter to `IN_PROGRESS`.** It did originally, which meant ticking off the final milestone flipped the roadmap to `COMPLETED` and 404'd the only endpoint that displays it, at exactly the moment the student finished. Caught in live verification, never by a test, because a mocked repository returns whatever it is stubbed with. Pinned now by `getMyRoadmap_CompletedRoadmap_StillReturned`. If a status filter is ever wanted again, give the student some other way to see a finished roadmap first.
- **`findByStudentIdOrderByStartedAtDesc` returns a `List`, not an `Optional`, and that is load-bearing.** A student who takes a second assessment gets a second recommendation and therefore a second roadmap — so the query legitimately matches several rows and an `Optional` finder would throw `IncorrectResultSizeDataAccessException` on exactly the second assessment. `getMyRoadmap` takes element 0, which the `DESC` ordering makes the newest, so a fresh recommendation still supersedes an older completed one. Same shape recommendation-service settled on for `findByUserIdAndIsActiveTrue`; the original task spec asked for an `Optional` here and it was wrong.
- **The unique constraint on `student_roadmaps(student_id, recommendation_id)` is the real idempotency guarantee**, not the `findByStudentIdAndRecommendationId` check in `generateRoadmap`. RabbitMQ is at-least-once, so a redelivery can race that check; the loser raises `DataIntegrityViolationException`, which the consumer's fail-soft catch discards. Same design as `student_profiles.userId`.
- **Seeding is a `CommandLineRunner`, not a `data.sql`** — the only service that does it this way. A runner executes after context refresh (so after `ddl-auto`), needs no `defer-datasource-initialization`, and sidesteps the `INSERT ... ON CONFLICT DO NOTHING` idempotency trap that cost assessment-service two SEV-2s. **Idempotency is checked per career (`existsByCareerNameIgnoreCase`), never a global `count() == 0`** — a count check would silently seed nothing on every existing deployment the day an eighth career is added, a failure indistinguishable from the seeder working. Proven by running `contextLoads` twice against live Postgres: 7 templates / 47 milestones both times.
- **`totalMilestones` on a `StudentRoadmap` is counted from the milestone rows actually copied, not read off `template.getTotalMilestones()`** — it is the denominator of `completionPercentage`, and reading it from the template would let the two disagree if a template were ever edited between the count and the copy.
- **`completedMilestones` is recomputed from `countByStudentRoadmapIdAndIsCompletedTrue` after every completion, never incremented in memory**, so the stored counter cannot drift from the rows it summarises. `completionPercentage` is rounded to 2 decimals — 1 of 7 is `14.285714285714286` raw.
- **`completeMilestone` loads by id and then compares the owner with `Objects.equals`, deliberately not `findByIdAndStudentId`.** That finder collapses "belongs to another student" (403) and "no such milestone" (404) into the same empty `Optional`, and this endpoint owes the caller both. `Objects.equals`, never `==`: both sides are boxed `Long` outside the Integer cache. Unlike organization-service, this does leak existence — unavoidable once 403 and 404 are distinguished at all.
- **Milestones are always read through `findByStudentRoadmapIdOrderByOrderIndexAsc`, never off the entity's LAZY collection.** That collection carries no `@OrderBy`, so it returns in whatever order Postgres chose, and the dashboard renders the checklist top to bottom without sorting.
- **Publishes `roadmap.updated` fail-soft and declares no queue for it.** Both rows are committed before the publish runs, so rethrowing would report failure for work that happened — and the retry would then hit the "already completed" 400. Pinned by `completeMilestone_BrokerDown_StillSucceeds`.
- **There is no endpoint that creates a roadmap.** The `recommendation.generated` consumer is the only path, so a student cannot request a roadmap for a career their assessment did not recommend. Consequence: anyone whose recommendation predates this service's first start has no roadmap and gets a permanent 404 on `/my` until they retake an assessment. Accepted deliberately.
- **`contextLoads` passes with RabbitMQ down.** The listener container logs `Failed to check/redeclare auto-delete queue(s)` and retries in the background rather than failing startup — so a green build proves nothing about the queue existing. Check the broker UI.
- No `spring.autoconfigure.exclude` (no security starter, so the class is absent and naming it fails startup), no `defer-datasource-initialization` (no `data.sql`), and no `management.health.rabbit.enabled` (already the default). Each omission is commented in `application.yml` so it does not get "restored".

PRS-service specifics worth knowing before touching it (third P1 service):
- **It consumes `student.registered`, NOT `user.registered`.** The original task spec called for a `user.registered` binding; no publisher in this system emits that key. Binding a topic queue to an unpublished key is not an error — the queue is created, the consumer starts, the broker UI looks healthy, and it receives nothing forever. `initialisePrs` would have become dead code and every row would have come from the defensive fallback, which looks exactly like the service working. Caught in planning by reading `auth-service`'s `RabbitMQConfig` rather than trusting the spec. There is a `do not "correct" this back` comment on the constant.
- **The weights now sum to 1.00 (40/30/20/10).** Until 2026-08-01 they summed to 0.90 with the 10% resume slot explicitly reserved for "a future resume builder" — resume-service is that builder. `PrsBreakdown`'s fields were renamed at the same time: `reservedWeight`/`reservedContribution` → `resumeWeight`/`resumeContribution`, plus a new `resumeScore` field, since "reserved" would now be actively misleading. A student who has never generated a resume keeps `resumeScore` at its entity default of `0.0`, so activating the weight did not silently move any existing score — verified live against the populated Docker table before and after the migration: every pre-existing row's `total_score` was unchanged. **Do not normalise weights "to reach 100"** — the whole point of storing four unweighted raw inputs is that a weight can be re-tuned without the stored values becoming meaningless, but the four contributions must still sum to `totalScore` exactly. Grades: `>=80 A`, `>=60 B`, `>=40 C`, `>=20 D`, else `F`, lower bound inclusive.
- **The four raw inputs are stored unweighted**; `totalScore` is always recomputed from all four, never incremented. Re-tuning a weight therefore does not invalidate stored data.
- **`updateResumeScore` mirrors `updateRoadmapScore` exactly** — same defensive `loadOrCreate`, same `recomputeAndSave` call, same fail-soft consumer pattern. It is the fourth `@RabbitListener` method on `PrsEventConsumer`, on its own queue (`careerbridge.prs.resume.queue`), never a listener added to an existing queue.
- **Adding `resumeScore` to a populated table needed `columnDefinition = "double precision not null default 0"`, not a bare `@Builder.Default`.** A `NOT NULL` column with no `DEFAULT` makes `ddl-auto`'s `ALTER` fail against existing rows, silently, as a WARN — the `Question.updatedAt` incident, then `StudentProfile.role`, now this. Verified the post-`ALTER` distribution directly rather than trusting a green `contextLoads`: all pre-existing rows backfilled to `0.0`, zero nulls.
- **`StudentServiceClient.fetchProfileScore` returns `-1.0` on any failure and that value must never be written to the entity.** It means "keep the last known `profileScore`", not a score. It is deliberately outside the legal 0–100 range so it fails a range check loudly if it ever leaks. Pinned by `updateAssessmentScore_ProfileCallFails_UsesExistingProfileScore` and verified live by stopping student-service mid-run: the roadmap input still updated and `profileScore` held at 30.0.
- **`RestClient` has no default timeouts and the call runs on a `@RabbitListener` thread at concurrency 1.** Connect and read are both pinned to 3s in `StudentClientConfig`. Without them one hung student-service stalls every subsequent PRS update indefinitely — the same failure JavaMail caused in notification-service. A fail-soft call with no timeout is not fail-soft; it just relocates the failure from an exception to a hang.
- **`student.service.url` defaults to `localhost:8082`, not `student-service:8082`.** The container hostname only resolves on the compose network, so a Docker default breaks `mvnw spring-boot:run`. docker-compose overrides it. Same convention as api-gateway's `${AUTH_SERVICE_URI:...}` placeholders.
- **The leaderboard is tenant-scoped**: SUPER_ADMIN ranks globally, ORG_ADMIN only within their own `organizationId`, everyone else 403. `organizationId` is harvested from `student.registered` — the only inbound event carrying it. An ORG_ADMIN with no `X-User-Org-Id` gets an **empty** list, never a global one; treating a missing header as "show everything" would be a cross-tenant leak triggered by an absent header. Verified live with two colleges: each admin saw exactly their own students.
- **`rank` is derived from list position, never stored** — the same student holds a different rank in a global list than in their own college's.
- **`findByStudentId` returns an `Optional`, and that is correct here** unlike roadmap-service's and recommendation-service's `List` finders: `uk_prs_student_id` genuinely makes `student_id` unique. The rule is *a single-result finder needs a unique constraint behind the queried columns* — it does here, it did not there.
- **Defensive record creation is fail-open.** An event for a student with no PRS row creates one rather than dropping the event, since the alternative leaves anyone who registered before this service first ran permanently invisible. Those rows carry a null `organizationId` and so never appear on a scoped leaderboard — omitting a student from their own college's board is the safer failure than leaking them onto another's.
- **Known accepted race:** `student.registered` and `recommendation.generated` arriving near-simultaneously can make `initialisePrs` and the defensive create collide. `uk_prs_student_id` stops the duplicate row, but the loser's exception is swallowed by the consumer's fail-soft catch and that one score update is lost until the next event. Registration precedes any assessment by minutes in practice, so this is documented rather than engineered around.
- **`contextLoads` passes with RabbitMQ and student-service both down** — the listener containers retry in the background and `RestClient` connects lazily. A green build proves neither that the queues exist nor that student-service is reachable.
- No `spring.autoconfigure.exclude` (no security starter), no `defer-datasource-initialization` (no `data.sql` — every row comes from an event), no `management.health.rabbit.enabled` (already the default). Each omission is commented in `application.yml`.

Recruiter-service specifics worth knowing before touching it (fourth P1 service):
- **Two REST clients, not one — student-service for the candidate pool, prs-service for candidate scores — and neither call goes through api-gateway.** Both are `SimpleClientHttpRequestFactory` beans with 3s connect + 3s read timeouts (`RestClientConfig`), same reasoning as prs-service's own client: a hung downstream would otherwise stall every candidate search or application submit indefinitely on a request thread.
- **The `RestClient` `@Bean` methods are named `studentRestClient`/`prsRestClient`, NEVER `studentServiceClient`/`prsServiceClient`.** The two client classes are `@Service`-annotated and component-scanned under exactly those second names; a `@Bean` method sharing a component-scanned bean's name is a `BeanDefinitionOverrideException` at startup — the app cannot start at all, while every unit test (none of which build a Spring context) stays green. Cost a SEV-2 here, caught only by `contextLoads`, logged in `ai_incident_log.md`. **Do not rename these to match the client class names.**
- **`PrsServiceClient` deliberately elevates its own role header.** `GET /api/prs/leaderboard` permits only `SUPER_ADMIN`/`ORG_ADMIN`; a `RECRUITER` calling it directly would be 403'd. Candidate search (RECRUITER-permitted) therefore sends `X-User-Role: SUPER_ADMIN` to prs-service internally, having already authorized the caller in its own service layer — legitimate because the call never leaves the compose network and the elevation is never echoed back to the caller. `getApplicationsForOrgStudents` elevates to `ORG_ADMIN` with the caller's real `orgId` instead, never to `SUPER_ADMIN`, so a `PLACEMENT_OFFICER` can never see another organization's roster through it.
- **`StudentServiceClient.fetchPublicProfiles` forwards the caller's REAL role**, unlike the PRS client — student-service runs its own RBAC on `/api/student/profiles/public`, and recruiter-service has no reason to override it.
- **Candidate search is exactly two HTTP calls, regardless of student count**: one to student-service for the whole public candidate pool, one to prs-service for the whole score leaderboard, then all filtering (skills, score range) happens in memory. The alternative shape — one profile fetch per candidate — is N+1 synchronous calls on a request thread at a 3s timeout each. If the candidate pool ever grows past what one response can carry, the fix is a filtered/paged endpoint on student-service, not a per-candidate loop here.
- **A missing PRS score is `-1.0` (`SCORE_UNAVAILABLE`), and the two score filters treat it asymmetrically on purpose.** `minScore` excludes it — "at least 60" is a claim the data cannot support for an unscored student. `maxScore` keeps it — "at most 60" has not been contradicted. Treating the sentinel as `0` would get both wrong. Verified live by stopping prs-service mid-search: candidates still returned (200, not 500) with `prsScore: -1.0`, `minScore=50` excluded them, `maxScore=50` kept them.
- **There is no `careerPath` field on `CandidateResponse` and no `?careerPath=` filter**, unlike the original task spec. The student's top recommended career lives in recommendation-service behind an `X-User-Id`-keyed `/my` endpoint with no batch/list form, so supporting it would mean a third REST client plus one synchronous call per candidate on every search. Add it only if recommendation-service grows a batch endpoint.
- **Interviews deliberately support multiple rounds per application — a deviation from the original task spec, confirmed with the user.** `interviews.application_id` carries **no** unique constraint, and every `InterviewRepository` finder returns a `List`, never an `Optional`, for the same reason recommendation-service's `findByUserIdAndIsActiveTrue` and roadmap-service's `findByStudentIdOrderByStartedAtDesc` do: *a single-result finder needs a unique constraint behind the queried column, and this one deliberately has none.* `scheduleInterview` accepts an application in status `SHORTLISTED` **or** `INTERVIEWED` — requiring only `SHORTLISTED` would make round two impossible, since the recruiter moves the applicant to `INTERVIEWED` after round one. There is no "already scheduled" 400 guard.
- **`updateInterview` re-validates the meeting-link rule against the entity AFTER the partial update is applied, not against the request alone.** Validating only the request would let a recruiter switch an `IN_PERSON` interview to `ONLINE` without supplying a link, leaving it silently linkless — caught while writing the service, pinned by `updateInterview_SwitchToOnlineWithoutLink_Throws400`.
- **`Company`/`Job`/`Interview` ownership checks use two different failure shapes on purpose.** Company and Job endpoints load by `(id, recruiterId)` compound finders, so another recruiter's row is a 404 — a recruiter has no legitimate reason to address another's company or job, so there is nothing to gain by distinguishing "doesn't exist" from "not yours". Application-status-update and interview endpoints load the job separately and compare `Objects.equals(job.getRecruiterId(), recruiterId)`, returning 403 — the recruiter addressed a *real* application or interview, and flattening that to "not found" would be misleading. `Objects.equals`, never `==`, throughout: both sides are boxed `Long` outside the Integer cache.
- **`deleteJob` is a hard delete, refused once `jobApplicationRepository.existsByJobId` is true** ("deactivate it instead") — applications, and any interviews hanging off them, reference the job id, so deleting it would strand a student's entire application history with no way to render it. `deactivateJob` is the soft path and is idempotent-refusing: deactivating an already-inactive job is a 400, not a silent no-op.
- **`companies` carries a `uk_company_recruiter_id` unique constraint on `recruiter_id`**, the real one-company-per-recruiter guarantee — `CompanyServiceImpl.createCompany`'s `existsByRecruiterId` check is only the TOCTOU fast path, same pattern as `student_profiles.userId` and `placement_readiness_scores.student_id`. `job_applications` carries `uk_application_job_student` on `(job_id, student_id)` the same way, for the duplicate-application guard.
- **No queue is declared for either published event.** `application.submitted` and `application.status.updated` have no consumer yet; a queue bound with no listener would accrue every event forever and look like an unprocessed backlog, same rule as `organization.created` and `prs.updated`. A future "you were shortlisted" notification-service consumer declares its own queue when it lands — do not add a second listener to an existing notification-service queue (see notification-service's own two-queues note).
- **`student.service.url` and `prs.service.url` both default to `localhost:<port>`, not the container hostname** — same convention as every other cross-service URL in this project (`AUTH_SERVICE_URI`, `STUDENT_SERVICE_URL` in prs-service). docker-compose overrides both.
- **`contextLoads` passes with RabbitMQ, student-service and prs-service all down** — this service declares no queue or listener at all (publisher-only), and both `RestClient`s connect lazily. A green build proves the application can start; it proves nothing about either downstream dependency. Both were verified separately against the live stack, including deliberately stopping each one mid-search.
- **The candidate pool depends on `StudentProfile.role`, added to student-service specifically to support this service** — see student-service's own note on it above. Without that filter, every registered user (including recruiters and admins) appeared as a candidate; caught in this service's own live verification, fixed in student-service, logged as its own SEV-3.

Resume-service specifics worth knowing before touching it (fifth P1 service):
- **OpenPDF, NOT iText 7.** iText Community is AGPL v3 — serving a generated PDF over HTTP is "conveying" under AGPL, which would oblige publishing this entire repository's source unless a commercial iText licence is purchased. OpenPDF (`com.github.librepdf:openpdf`, package root `com.lowagie.text.*`) is an LGPL/MPL fork of the iText 4 lineage: same flowing `Document`/`Paragraph` API shape, no licence exposure. Its API was verified by decompiling the jar before writing any PDF code, not assumed from iText 7 examples — `java.awt.Color`, not `DeviceRgb`; `Document`'s constructor margin order is `(left, right, top, bottom)`, not the CSS order.
- **The generated PDF lives in `student_resumes.pdf_content`, a `bytea` column — not on disk, no Docker named volume.** Removes the entire "row exists but the file is missing" failure mode a disk-backed design would need to handle, and survives container restarts and multiple replicas for free, which a named volume would not once there is more than one replica. `@Column(columnDefinition = "bytea")`, never `@Lob`: Hibernate's `PostgreSQLDialect` maps a bare `@Lob byte[]` to the `oid` large-object type the same way it maps `@Lob String`, and the ORM insert path cannot fill an `oid` column from a plain byte array either. Verified against the live schema, not assumed: `pdf_content bytea`.
- **List endpoints (`GET /my`, `GET /student/{id}`) read through `ResumeSummary`, a Spring Data interface projection that excludes `pdfContent`** — the first projection in this codebase; every other repository returns full entities. A plain entity finder for a list would pull every PDF into memory just to render a metadata table, since JPA has no cross-provider guarantee for lazy-loading a `byte[]` column.
- **The ATS keyword map is keyed on the seven real careers** (`Full Stack Developer`, `Backend Developer`, `Frontend Developer`, `Data Scientist`, `DevOps Engineer`, `Mobile Developer`, `System Design Engineer`), verified against `CareerCatalog.java` (recommendation-service) and `RoadmapDataSeeder.java` (roadmap-service) rather than assumed — the original task spec named two careers ("Android Developer", "Cloud Engineer") that do not exist anywhere in this system. **This is now a fourth copy of the career list**, after `assessment-service/data.sql`, `CareerCatalog.java` and `RoadmapDataSeeder.java`; a rename on any of those three sides is silent here, since the keyed lookup simply stops matching and every student falls through to best-match. There is no `StudentProfileDto.careerPath` — no such field exists on the profile — so the keyed lookup is currently unreachable; only best-match runs.
- **`AtsScoreCalculator` scores every career independently and takes the highest PERCENTAGE, never the highest raw match count.** A career with 5 of 10 keywords (50%) must outrank one with 6 of 13 (46.15%) even though 6 > 5. A count-first implementation gets this backwards. Pinned by `calculate_PrefersBestRatioOverHighestCount`, with skills chosen so no keyword overlaps between the two competing lists.
- **The identical null-list-entry NPE was written in both `AtsScoreCalculator` and `ResumePdfBuilder`, fixed once in each, one step apart.** `ResumePdfBuilder`'s `addSkills` was fixed first (Step 5); `AtsScoreCalculator`'s `calculate` had the exact same shape and was not revisited until its own test caught it in Step 10. Both now filter `Objects::nonNull` before mapping `SkillDto::getSkillName`, and the calculator's comment points at the builder so the pairing is explicit. Worth treating as a category — "same fix, second location" — not two coincidences; the `RestClient` bean-naming collision in recruiter-service was the first instance of this pattern.
- **`downloadResume` is a single repository read, returning a `ResumeDownload` carrying both the bytes and the stored `fileName`.** An earlier draft called the service twice — once for metadata to get the filename, once for the bytes — which was also two chances for the RBAC check to disagree with itself between calls. Caught and fixed before it shipped.
- **A STUDENT reading another student's resume by id is a 404, never a 403** — deliberately the opposite RBAC shape from recruiter-service's application/interview lookups. A student has no legitimate reason to address a resume id that is not theirs, so answering 403 would confirm the row exists; company/job lookups in recruiter-service use the same 404 shape for the same reason. `RESUME_VIEWER_ROLES` (RECRUITER/PLACEMENT_OFFICER/ORG_ADMIN/SUPER_ADMIN) read by unscoped id — the role check alone is the gate.
- **`StudentServiceClient.fetchMyProfile` returns `null` on any failure, and the service turns that into a 503, not a 500** — the fault is a downstream dependency being unreachable, and the client should retry. Verified live: student-service stopped mid-request, `POST /generate` returned 503 in ~3.4s (the configured `RestClient` timeout firing), never a hang, and no resume row was written.
- **The event is published inside the `@Transactional` method, after the row is committed to the same transaction** — consistent with prs-service's and recruiter-service's existing pattern, so a consumer could theoretically read before the outer commit flushes. Flagged, not changed, since two services now react to this one event rather than zero or one.
- **No queue is declared in `resume-service`'s own `RabbitMQConfig`**, even though `resume.generated` has two real consumers — prs-service and student-service each declare their own queue for it, per the project's one-queue-per-consumer-per-event rule. A queue on the publisher side would either duplicate theirs or, worse, sit unconsumed and accrue every event forever.
- **`student-service`'s second consumer method (`onResumeGenerated`) is routed through a new `StudentService.updateResumeUrl` method, never straight to the repository.** The write needs `recalculate()`'s private path — the same one `updateProfile`/`addEducation`/`addSkill`/`addProject` already use — or `profileCompletionPercentage` would silently desync the moment `resumeUrl` changed. `StudentServiceImpl` gained its first `Logger` for this.
- **`resumeUrl` closes a real, pre-existing gap**: `ProfileCompletionCalculator` has always awarded 15 of 100 points for a filled `resumeUrl`, but nothing in the system ever wrote it (`StudentProfileRequest` explicitly excludes it as server-derived) — every student was permanently capped at 85% completion until this branch. Verified live: `profileCompletionPercentage` rose exactly 35 → 50 the moment `resume.generated` was consumed.
- **Accepted edge case, not fixed:** deleting a student's *last* resume in resume-service does not clear `resumeUrl` in student-service, since there is no `resume.deleted` event. A student who deletes their only resume keeps the 15% and a URL that now 404s until they generate a new one.
- **`contextLoads` passes with RabbitMQ and student-service both down** — this service declares no queue or listener at all (publisher-only), and its `RestClient` connects lazily. A green build proves the application can start; it proves nothing about either downstream dependency. It is not a formality here either way: recruiter-service shipped a `RestClient` `@Bean` named after its own component-scanned client class and could not start at all while 84 unit tests stayed green — `contextLoads` was the only thing that caught it, and this service's bean is deliberately named `studentRestClient`, not `studentServiceClient`, for exactly that reason.
- **Live verification exposed a real Postgres capacity ceiling, unrelated to any application code.** `docker exec ... psql` failed with `sorry, too many clients already` within seconds of bringing the stack up, before a single verification query ran. Root cause: the image's stock `max_connections=100`, and ten PostgreSQL-backed services now share it, none overriding HikariCP's default `maximumPoolSize`/`minimumIdle` of 10 — at steady state that is exactly 100 connections with zero headroom for anything else, including a diagnostic session. resume-service was the tenth service and tipped it over. Fixed via `command: postgres -c max_connections=300` on the `postgres` service in `docker-compose.yml`; all twelve dependent containers reconnected transparently with no data loss. 300 is headroom for now, not indefinitely — revisit if an eleventh or twelfth PostgreSQL-backed service is added.

AI-coach-service specifics worth knowing before touching it (sixth P1 service):
- **`recommendation.generated` carries NO milestone data, and that is why this service has no RabbitMQ consumer, no queue, and no `spring-boot-starter-amqp` dependency at all.** The original build prompt was designed around consuming that event "for each milestone topic"; its real payload is six fields (`userId`, `recommendationId`, `topCareerName`, `matchPercentage`, `categoryName`, `generatedAt`) and a case-insensitive grep for "milestone" across all of recommendation-service returns **zero hits**. Milestones exist only in roadmap-service, materialised from 47 seeded templates. Had that design shipped, `event.getMilestones()` would be null on every delivery: the consumer logs "nothing to enrich", the queue shows real traffic, and not one resource is ever created. **Do not "restore" an event consumer here** — the trigger is deliberately an admin POST.
- **The resource catalog is keyed `(careerName, milestoneTitle)`, NOT `(studentId, milestoneTitle)`.** Both external search queries are built from `milestoneTitle + careerName` and contain **zero student-specific data**, and milestone titles are copied verbatim from the 47 fixed templates — so per-student rows would be byte-identical duplicates. Shared: 47 documents and 94 lifetime API calls, forever. Per-student: 7 documents and 14 API calls each, which at YouTube's 100-searches/day free quota caps the whole platform at **~14 students per day** before a hard 403. This is the single decision that makes Feature A viable on free tiers; do not "personalise" it without a new data source that actually differs per student.
- **Never persist a `MilestoneResourceDocument` with an empty `resources` list.** `existsByCareerNameAndMilestoneTitle` is the skip check at the top of `CatalogRefresher.processMilestone`, so an empty placeholder makes that milestone **permanently un-enrichable** — every future refresh skips it and the student never gets resources for it. Pinned by `run_NoResourcesFound_DoesNotPersistPlaceholderDocument`. Highest-value guard in this service.
- **`GET /api/roadmap/my` returns 404 for a student with no roadmap, which is a real state, not a fault.** `RoadmapServiceClient.fetchMyRoadmap` is therefore three-state: `HttpClientErrorException.NotFound` → `null` (caller returns `[]`), anything else → `CustomException` 503. **Never use `.onStatus(4xx, noop)` here** — Jackson 3 has `FAIL_ON_UNKNOWN_PROPERTIES` off, so a 404 error body binds cleanly into an all-null `RoadmapResponseDto` and a genuine outage becomes indistinguishable from "no roadmap". The two clients that are plain fail-soft (`StudentServiceClient`, `PrsServiceClient`) return `null` and only thin out the coaching prompt.
- **Groq write order is load-bearing: build prompt → call Groq → persist BOTH turns in one save.** The state that must never occur is a persisted user turn with no assistant reply — it is unanswerable, it re-enters the 20-message history on every subsequent request, and it silently doubles token cost forever. On any Groq failure nothing is written and the client retries with the same text. Same reasoning as notification-service's documented Mongo→email→Postgres ordering. Pinned by `sendMessage_GroqFails_PersistsNothing`. This is also why `ChatMessage` is **embedded on `ChatSession`** rather than a second collection: both turns land in one atomic single-document write, so there is no half-written state to reason about.
- **No `Executor`/`TaskExecutor` `@Bean` anywhere in this service, deliberately.** `TaskExecutorConfigurations` is gated by `@ConditionalOnMissingBean(Executor.class)`, so declaring one **suppresses Boot's own `applicationTaskExecutor` entirely** — while `ApplicationTaskExecutorAsyncConfigurer` still resolves that bean *by name*, lazily. The result is a latent `NoSuchBeanDefinitionException` that fires the first time an unqualified `@Async` actually runs and that `contextLoads` cannot catch. Serial execution comes from `spring.task.execution.pool.core-size: 1` in `application.yml` instead: with the default unbounded queue a `ThreadPoolTaskExecutor` never grows past core-size, which is what makes the 300 ms inter-milestone sleep meaningful. `spring.threads.virtual.enabled` defaults `false`, so no virtual-thread executor breaks this.
- **`@EnableAsync` is required on the main class** — Boot 4 auto-configures the executor but never registers the `AsyncAnnotationBeanPostProcessor`. And **`CatalogRefresher` must stay a separate bean from `AiCoachResourceServiceImpl`**: a self-invoked `@Async` call bypasses the proxy and runs synchronously on the request thread, turning a 202 into a multi-minute hang.
- **`contextLoads` passes with NOTHING running — no Mongo, no Postgres, no RabbitMQ.** Verified empirically, not assumed: nothing on the context-refresh path opens a socket for a plain `mongodb://` URI (`MongoAutoConfiguration`, `MongoDatabaseFactoryConfiguration`, `MongoRepositoryFactory` all construct only), and `autoIndexCreation` defaults `false`. **This is the only service in the repo with that property** — every other one needs its gitignored `application-local.yml` plus a live datastore. Three things preserve it: keep the tracked default a plain `mongodb://localhost`, never a `mongodb+srv://` (the driver resolves SRV TXT records **eagerly** in `ConnectionString`'s constructor and would need working DNS); keep `spring.mongodb.database` set (`MongoDatabaseFactoryConfiguration` asserts `hasText`); and **never set `spring.data.mongodb.auto-index-creation: true`**, which issues `createIndex` during refresh.
- **No `@Indexed(unique = true)` on `(careerName, milestoneTitle)`, for two compounding reasons.** It would be a silent no-op (`autoIndexCreation` is false project-wide, same note as notification-service), and enabling auto-index-creation to make it work would forfeit the no-Mongo-required `contextLoads` above. The `existsBy...` check plus a single-replica `AtomicBoolean` is the real guard. Create the index by hand in Atlas if this ever runs with more than one replica.
- **`ChatSessionRepository.deleteByIdAndStudentId` returns `long`, never `List`.** A derived delete returning `List<T>` runs `findAllAndRemove`, loading every match into memory first. `0` means either "no such id" or "belongs to another student" — both correctly collapse to 404, the same shape resume-service uses for resume lookups and for the same reason: a student has no legitimate reason to address a session id that is not theirs, so 403 would confirm existence.
- **`GET /api/ai-coach/resources` is exactly two round trips regardless of milestone count** — one `GET /api/roadmap/my`, one `findByCareerName`, then matched in memory. Pinned by `getMyResources_AnyMilestoneCount_QueriesCatalogExactlyOnce`. The response contract distinguishes two states at no extra cost: `[]` means the student has no roadmap; a list where every entry has `resources: []` means the roadmap exists but the catalog has not been refreshed yet.
- **`POST /resources/refresh` fetches the templates SYNCHRONOUSLY before returning 202.** One internal call at a 3s timeout; an admin getting an immediate 503 when roadmap-service is down beats a 202 followed by silence. The `AtomicBoolean` CAS also happens on the request thread, before dispatch, and is released in a `finally` inside the `@Async` method — an exception thrown from a `void @Async` method only reaches `SimpleAsyncUncaughtExceptionHandler`, never the caller.
- **`RoadmapServiceClient.fetchAllTemplates` forwards the caller's REAL role — no elevation**, unlike recruiter-service's `PrsServiceClient`. `GET /api/roadmap/templates` permits SUPER_ADMIN/ORG_ADMIN, and the refresh endpoint already requires SUPER_ADMIN in its own service layer before the client is ever reached, so there is nothing to elevate.
- **Six `RestClient` beans, all named `*RestClient`, never `*ServiceClient` or a bare provider name.** `StudentServiceClient`, `PrsServiceClient`, `RoadmapServiceClient`, `GroqClient`, `TavilyClient` and `YouTubeClient` are all component-scanned `@Service`/`@Component` classes — a `@Bean` method matching any of those names is a `BeanDefinitionOverrideException` at startup, invisible to every unit test. Two timeout tiers: 3s/3s for the three internal services, 5s/10s for the three external APIs. Every consuming constructor carries a `@Qualifier`, which is mandatory here rather than optional: with six beans of the same type, injection by type alone is ambiguous.
- **`URI.create(url).getHost()`, never `new java.net.URL(url)`** — the latter is `@Deprecated(since = "20")`. Two failure modes, not one, confirmed by probing Temurin 21: `URI.create` throws `IllegalArgumentException` on syntactically invalid input **and** returns `null` for a relative string or a host containing an underscore. `TavilyClient.domainOf` handles both and is pinned by four tests.
- **All three external clients check `StringUtils.hasText` on their key before calling out.** A blank key gives a clear 503 ("AI coach is not configured yet") or an empty resource list, rather than sending `Authorization: Bearer ` and getting an opaque upstream 401. This is what lets the whole service — and `mvnw clean install` — stay green with no API keys at all.
- **The external wire formats (Groq/Tavily/YouTube DTOs) are written from documentation and are UNVERIFIED against a live call**, since no API keys existed when this shipped. Each provider's request and response classes live in one file under `dto/external/` precisely so a shape correction is a single-file edit. `groq.model` is a config value (`${GROQ_MODEL:llama-3.3-70b-versatile}`) because Groq deprecates models fairly often — a rename is an env change, not a rebuild.
- **Prompt injection is mitigated, not eliminated.** The system prompt interpolates student-controlled fields (`firstName`, `skillName`), so a student can name a skill `"Ignore previous instructions"`. Guards are a `@Size(max = 2000)` on message content, `MAX_HISTORY = 20`, a 15-skill cap, and newline flattening on every interpolated field. Blast radius is genuinely small — no tool use, no other user's data reachable, and the gateway-injected `X-User-Id` means a student can only steer their own session — so the honest framing is cost control, not compromise. Neither the assembled prompt nor any API key is ever logged.
- **No cap on session count or lifetime message count per student.** Only per-message length and per-request history are bounded. Add a cap only if the Groq quota becomes a real constraint.

API-gateway specifics worth knowing before touching it:
- **Servlet, not reactive.** The dependency is `spring-cloud-starter-gateway-server-webmvc` (Tomcat) — Spring Cloud Gateway 5 split reactive and servlet into separate starters, and the old catch-all `spring-cloud-starter-gateway` no longer exists at this version (404 on Maven Central). Consequence: no `Mono`, no `ServerWebExchange`, no `AbstractGatewayFilterFactory`, no `ErrorWebExceptionHandler` — those are reactive-only APIs and are not on this classpath. Authentication is a plain `OncePerRequestFilter`, the same mechanism auth-service uses for its own filter.
- **Routes bind under `spring.cloud.gateway.server.webmvc.routes`, NOT `spring.cloud.gateway.routes`.** The bare key was correct for SCG ≤ 4.1 and is what most online examples still show; under SCG 5 it binds to nothing, with no warning and no startup failure — the app reports healthy and every `/api/**` request 404s as if the route simply didn't exist. Logged SEV-2 in `ai_incident_log.md`, reproduced with an A/B test on the same jar (old prefix → 404, new prefix → 500-with-upstream-down, proving the route matched).
- **Three identity headers are injected, not one: `X-User-Id`, `X-User-Role`, `X-User-Org-Id`.** All three come from JWT claims (`userId`, `role`, `organizationId`) that auth-service has always written. The set of headers the gateway owns lives in `GatewayIdentityRequestWrapper.MANAGED_HEADERS` — **a name in that set is stripped from client input whether or not the gateway has a replacement**, which is the whole security property. Until organization-service landed, only `X-User-Id` was managed, so a client-supplied `X-User-Role: SUPER_ADMIN` passed straight through; anything that starts trusting a new header downstream must be added to `MANAGED_HEADERS` in the same change, never later. `X-User-Org-Id` is legitimately **absent** for SUPER_ADMIN (nullable `User.organizationId`), so downstream services must read it with `required = false`.
- **The `X-User-Id` header is stripped and reinjected on *every* request, including public ones.** `JwtAuthenticationFilter` wraps the `HttpServletRequest` unconditionally; on a public path the wrapper carries a `null` id, which hides any client-supplied `X-User-Id` rather than passing the raw request through. Every downstream service trusts this header blindly and has no Spring Security of its own (see student-service notes above), so a bare `chain.doFilter(request, response)` on the public-path branch would let any caller impersonate any user with one `curl -H "X-User-Id: 1"`. Verified live: a spoofed header on both a protected route (with a valid token) and a public route (with no token) never reaches the downstream service. Pinned by two tests.
- **All three `HttpServletRequestWrapper` header methods must be overridden — `getHeader`, `getHeaders`, and `getHeaderNames`.** Spring's `ServletRequestHeadersAdapter`, which is what the gateway's proxy step actually reads from, enumerates via `getHeaderNames()` and then calls `getHeaders(name)` — it does not call `getHeader(String)` at all. Overriding only `getHeader` compiles cleanly and is a silent no-op: the injected header would never leave the gateway. Verified by proxying through a real downstream stand-in and reading back what it received.
- **`userId` claim: `claims.get("userId", Long.class)`, never a `(Long)` cast.** auth-service writes the claim as a `Long`, but JSON only has "number", so Jackson deserializes anything under 2³¹ back as an `Integer` — which is every real user id. A cast throws `ClassCastException` on the first authenticated request. jjwt's typed accessor widens correctly.
- **HS384, not HS256** — same 49-byte-secret rule as auth-service (see below); this gateway must derive the key exactly the same way (`Keys.hmacShaKeyFor`, no explicit algorithm) or verification fails for every token.
- **`gateway.jwt-secret` must stay byte-identical to auth-service's `jwt.secret`.** One signs, the other verifies; there is no `application-local.yml` for this service because the committed default already matches auth-service and there is no other secret to protect.
- **Public paths are three specific auth endpoints — `/api/auth/login`, `/api/auth/register`, `/api/auth/refresh` — plus `/actuator/**`, `/api/recommendation/careers`, and the Swagger surface.** This was `/api/auth/**` until the admin module landed, and the wildcard was **not** harmless: a public path is forwarded with `identityHeaders(null, null, null)`, so `/api/auth/admin/**` reached auth-service with no `X-User-Role` and 400'd on the required header — unreachable rather than insecure, but broken. `/api/auth/refresh` can never be JWT-validated (refresh tokens are opaque UUIDs checked against a Postgres table, not JWTs — see auth-service specifics); `/login` and `/register` are how a caller obtains a token in the first place. **`/api/auth/logout` requires a valid token and is intentionally protected** — auth-service's own `SecurityConfig` has always permitted only register/login/refresh and fallen through to `.anyRequest().authenticated()`, so the gateway now agrees with the service rather than forwarding a request it will reject. There is no `/api/assessment/careers` — that endpoint does not exist on assessment-service; don't re-add it from the original spec without checking.
- **No Spring Security dependency, and none of the five backend services has one either.** `config/SecurityConfig.java` is a deliberately empty stub, same convention as student-service's — the servlet filter does the authentication, and a full Spring Security filter chain here would immediately need `permitAll` everywhere, which is ceremony around code that already exists.
- Eureka client dependency was removed — nothing in this repo configures a discovery server, routes are hardcoded `localhost:<port>` URIs, and the dependency only produced continuous connection-refused log noise.
- Since this gateway is the only thing validating a JWT, **ports 8081–8089 must not be publicly reachable** at deploy time — the same constraint already noted for student-service's port 8082, now true of all eight backend services. `docker-compose.yml` already enforces this by publishing no host port for any of them.

Neither implements Spring's `ErrorResponse`, so both return a misleading HTTP 500 without an explicit handler. Both are logged incidents; see `ai_incident_log.md`. (student, assessment, recommendation and notification all have both — recommendation verified against a live server.)
- **auth-service is missing `MethodArgumentTypeMismatchException`** — it has 4 handlers where the other four services have 5. The fix from `ai_incident_log.md` (2026-07-25) was never back-ported to it. Lower risk there because its endpoints take JSON bodies rather than a numeric `X-User-Id` header, so nothing triggers it today — but any `@PathVariable Long` or numeric `@RequestParam` added later returns a 500 for a plain client typo. One-line fix on its own branch; do not fold it into another service's work.
- If a future service needs a reserved word as a column name (e.g. `rank`, `order`, `group` — reserved in both MySQL and PostgreSQL), quote it explicitly — `@Column(name = "\"rank\"")` — and confirm with `hibernate.auto_quote_keyword` off (the project default). ddl-auto silently fails on an unquoted reserved word. See recommendation-service's `CareerRanking.rank`.
- Each team member must create their own gitignored `application-local.yml` per PostgreSQL-backed service (`auth-service`, `student-service`, `assessment-service`, `recommendation-service`, and the rest as they are built) with their real DB password, or `mvnw clean install` fails on `contextLoads`. Add to team setup notes.
- **All 10 databases must exist before any service starts** (`CREATE DATABASE careerbridge_auth;` `_student;` `_assessment;` `_recommendation;` `_notification;` `_organization;` `_roadmap;` `_prs;` `_recruiter;` `_resume;` — PostgreSQL has no `createDatabaseIfNotExist` JDBC flag, unlike MySQL). Add this to team setup notes alongside the `application-local.yml` step. Under Docker `docker/init.sql` handles it, but only on a fresh `postgres-data` volume — an existing one needs each new database created by hand. **Still 10, not 11: ai-coach-service uses MongoDB only and `docker/init.sql` was deliberately not touched for it.**
- **Postgres `max_connections` was raised to 300** (`command: postgres -c max_connections=300` on the `postgres` service in `docker-compose.yml`) after ten PostgreSQL-backed services exhausted the image's default 100 within seconds of `up -d` — none override HikariCP's default pool of 10, so ten services at steady state is exactly 100 connections with no headroom for anything else. Revisit if an eleventh or twelfth service is added. **ai-coach-service is the eleventh backend service but adds ZERO connections** (MongoDB only), so the ceiling is unchanged — the count that matters is PostgreSQL-backed services, still ten.
- **ai-coach-service's three external APIs are unverified against live keys.** Groq, Tavily and YouTube Data API v3 keys did not exist when the service was built, so the request/response DTOs in `dto/external/` are written from documentation and have never seen a real response. When keys arrive: set `GROQ_API_KEY`/`TAVILY_API_KEY`/`YOUTUBE_API_KEY` in `.env`, `POST /api/ai-coach/resources/refresh` as SUPER_ADMIN, then verify `db.milestone_resources.countDocuments()` is 47 with **zero** documents holding an empty `resources` array. - **ai-coach-service is the only service whose `mvnw clean install` is green on a fresh clone with nothing running** — no Atlas, no PostgreSQL, no RabbitMQ, no `application-local.yml`. Three things preserve that and are easy to break: the tracked default must stay a plain `mongodb://localhost` (a `mongodb+srv://` resolves DNS TXT records eagerly at context refresh), `spring.mongodb.database` must stay set, and `spring.data.mongodb.auto-index-creation` must stay off. If a future change makes this service need a live datastore for `contextLoads`, say so explicitly rather than letting the property rot silently.
- **A `@Bean` method must never share a name with a `@Service`/`@Component`-scanned class it feeds.** recruiter-service named two `RestClient` beans after the client classes they were injected into (`studentServiceClient`, `prsServiceClient`), which collided with Spring's default component-scan name for those same classes — `BeanDefinitionOverrideException` at startup, invisible to every unit test because none of them build a Spring context. `contextLoads` is what caught it. Rule for any future `@Bean`-per-downstream-client pattern: name the bean after what it *is* (`studentRestClient`), never after what it *feeds*.
- **A column added to a populated table and then used in a query `WHERE` clause is two changes, not one.** `StudentProfile.role` (added for recruiter-service's candidate search) is a second instance of this after `Question.updatedAt`: the nullable-column `ALTER` succeeds silently, but every pre-existing row then fails the new filter, and the endpoint returns an empty result with no error anywhere. - **recruiter-service's `application.submitted`/`application.status.updated` have no consumer** — scoped out deliberately, same pattern as `organization.created`/`prs.updated`. ## Admin Module — feature/admin-module (assessment-service additions)

### assessment-service changes

**Question entity (model/Question.java)**
- Added `isActive` (Boolean, @Builder.Default=true, NOT NULL DEFAULT true) — DDL-auto backfilled all 22 rows
- Added `updatedAt` (LocalDateTime, @UpdateTimestamp)
- No DataMigrationRunner — @Builder.Default + PostgreSQL column DEFAULT handled backfill automatically

**QuestionRepository additions (Step 8)**
- Removed unfiltered finders; replaced with:
  - `findByCategoryIdAndIsActiveTrueOrderByOrderIndexAsc` — student pool + validation
  - `countByCategoryIdAndIsActiveTrue` — ≥N guard
  - `findAllByOrderByCategoryIdAscOrderIndexAsc` — admin listing (all questions, including inactive)
- Deleting the old finders (not adding alongside) enforced the migration as a compile error — caught 12 stale references immediately

**Admin DTOs**
- AdminOptionRequest: text, weight (Integer 0–3, @NotNull @Min(0) @Max(3))
- AdminOptionResponse: id, text, weight
- AdminQuestionRequest: text, categoryId, orderIndex, isActive (@Builder.Default=true), options (@Size(min=2,max=4), @Valid)
- AdminQuestionResponse: id, categoryId, categoryName, text, orderIndex, isActive, options, createdAt, updatedAt
- isCorrect was deliberately NOT used — assessment-service uses a graded weight model (0–3), not binary correct/incorrect. Seed data confirmed: 0 violations of exactly-one-max-weight across all 22 questions.

**AdminQuestionService + AdminQuestionServiceImpl**
- 6 methods: addQuestion, editQuestion, getQuestion, listQuestions(categoryId nullable), activateQuestion, deactivateQuestion
- RBAC: SUPER_ADMIN and ORG_ADMIN only; others throw CustomException 403 "Only SUPER_ADMIN or ORG_ADMIN may manage the question bank"
- Exactly-one-max-weight guard on addQuestion AND editQuestion — uses `.intValue() == AssessmentConstants.MAX_OPTION_WEIGHT`, never ==
- editQuestion: full option replace (deleteByQuestionId then save new). Safe because AttemptAnswer stores awarded weight, not a live FK to Option
- Weight guard runs BEFORE deleteByQuestionId — a rejected edit cannot strand a question with zero options
- deactivateQuestion: soft-only, logs WARN if category drops below MIN_QUESTIONS_PER_CATEGORY, does not hard-refuse
- No DELETE endpoint — deactivation is permanent soft-retire to protect historical AttemptAnswer rows
- listQuestions: 3 queries flat (questions → categories → options), assembled in memory. Uses findByQuestionIdInOrderByOrderIndex scoped to fetched IDs
- Option entity uses Long questionId (not @ManyToOne), field is optionText, no built-in delete method → added deleteByQuestionId to OptionRepository
